# 自动上滑助手（AutoSwipe Helper）

针对「免费短剧 / 听书类 App 播完一集不自动进下一集、广告倒计时结束也不自动继续」的小工具。

纯 Java、零第三方依赖、**不需要 root**，原理是 Android 无障碍服务（AccessibilityService）：
监测播放页状态，在合适时机补一个动作（上滑一次 / 点一下按钮）。

目前覆盖：

| App | 包名 | 需要的动作 |
| --- | --- | --- |
| 红果免费短剧 | `com.phoenix.read` | 竖屏**上滑**切下一集 |
| 红果免费漫剧 | `com.kylin.read` | 竖屏**上滑**切下一集 |
| 番茄畅听 | `com.xs.fm` | 点**「下一章 / 继续播放」** |
| 番茄免费小说（听书） | `com.dragon.read` | 点**「下一章 / 继续播放」** |

## 已验证的问题背景

**红果免费短剧**

- 红果本身「默认开启下一集自动播放」，正常一集播完会自己滑到下一集。
- 但**每集之间的贴片广告**播完后经常不续播，要手动点/滑一下。
  今日头条、B 站、抖音评论区大量用户反馈，不是个例。
- 其中**直播类广告**尤其明显：广告放完会停在直播画面上，底部显示
  「上滑继续看短剧」，但不会自动滑。这属于"该 App 自己都提示你手动滑了"，
  是最可靠的触发信号，工具为此加了专门规则（T0）。

**番茄畅听**

- 同样有「自动播放下一集」开关，位置在 我的 → 设置 → 播放设定。
- 它的广告机制和红果不同：番茄畅听是**「看广告赚畅听时长」**，广告会和
  时长限制、金币任务绑在一起，因此除了「不自动下一集」，还常见
  「广告看完不自动继续播放、要手动点」「广告加载失败 / 活动繁忙」。
- 关键区别：**番茄畅听是音频 App，没有"上滑"手势**。它需要的是
  点「下一章 / 继续播放 / 继续收听」按钮 —— 本工具为此专门加了
  「广告结束后自动点播放按钮」这条规则。

| 规则 | 作用 | 默认 |
| --- | --- | --- |

| 自动点「跳过」广告 | 识别到「跳过」就点掉 | 开 |
| **出现「上滑继续看短剧」提示时自动上滑** | **红果直播类广告用这条，优先级最高**；广告页上出现 1 次就动手，其它情况要连续出现 2 次（约 4 秒） | 开 |
| 检测到直播间广告（「点击进入直播间」等） | 直播间广告页的锚点判定 | 开 |
| **直播广告兜底：见过直播间锚点、且这一页从那时起可见文字一点没变** | **读不到上面两条文案时用**；只对"同一页"生效，同一页只补一次 | 开，10 秒 |
| 广告结束后自动上滑 | 短剧类：广告消失后补一次上滑 | 开 |
| 广告结束后自动点「播放/继续播放」 | **听书类**：广告消失后点播放按钮恢复 | 开 |

| **画面静止检测：连续 N 秒画面完全不动就上滑** | **一集播完卡住时用这条**，截图对比，不依赖任何文案 | 开，15 秒 |
| **疑似广告页兜底：屏幕上看不到集数标签 + 可见文本很少 + 文字长时间不动就前进** | **全屏直播广告页用这条**（提示、锚点都读不到时），触发后静默 90 秒 | 开，15 秒 |

| 定时自动上滑 | 兜底方案 | 关，45 秒 |

## 调参建议

1. **先确认没被冻结**：`[状态]` 行里的 `重要性=` 应该 ≤300（最好 125），`冻结=` 应该是 0 次。
   如果出现 `⚠ 整个进程曾被暂停` / `⚠ 保活服务也被冻结`，先去做上面的省电、白名单、
   自启动设置，再谈判定规则——被冻结时任何规则都不会执行。
2. **再读判定日志**：日志会打印是否进入目标应用、识别到的集数、是否检测到广告、
   广告结束、是否点到「播放/跳过」、是否命中「上滑继续看短剧」提示、上滑是否下发成功。
3. 直播类广告卡住时，日志里应出现
   `检测到「上滑继续看短剧」提示，执行上滑` 与 `上滑（上滑提示）-> 已下发`。
   如果只有前者没有后者，说明手势被系统拦了；两条都没有，先看状态行里的
   `上滑提示=弱`（文案在树里但被标成"不可见"，由「弱提示兜底」处理）；
   连 `弱` 都没有、说明这行文案根本不在无障碍树里，此时看日志里的
   `[自动抓屏]` / `[锚点]` 现场，或者手动点「立即抓一次屏」补关键词。
   另外，如果是那种"整页盖住、读不出一个字"的直播广告（状态行 `可见文本=0`、`集数=…(不在屏上)`），
   由「全屏直播广告快滑」负责，默认 5 秒动手；嫌慢/嫌快就调「全屏广告页判定秒数」。
4. 日志提示**读到进度文字但它一直不动 / 读不到进度信号**时，「进度停滞上滑」会被
   自动停用（防止整集播放中途被误滑），这时改用「定时自动上滑」或依靠文案锚点。
5. 番茄畅听若广告后仍不恢复：确认「广告结束后自动点播放按钮」是开的；
   若日志里没出现点击记录，说明按钮文案不在识别表里，需要补充关键词。
6. 「立即测试上滑」按钮可验证手势本身是否生效（听书类用不上，短剧类有用）。
7. 想知道某个 App 的包名：勾选「调试：记录前台应用包名」，打开那个 App 待一会，
   回来读日志里的「前台应用包名: xxx」，再填进「目标应用包名」。

## 根因：本进程被系统冻结（Honor 实测）

真机上最重要的一次排查结论：**工具没生效的原因不是判定逻辑，而是整个进程被系统冻结了。**

Honor（MagicOS）会把"没有前台界面、只在后台干活"的应用整体冻结（进程被 SIGSTOP），
这段时间里 App 里**所有线程、所有回调都停摆**，日志里只会周期性出现：

    15:27:14  ⚠ 整个进程曾被暂停 17969ms（疑似被 ROM 冻结，累计 1 次）
    15:31:56  ⚠ 整个进程曾被暂停 214524ms（疑似被 ROM 冻结，累计 4 次）

冻结期间的直接表现：

- **一条 `[状态]` 都没有**，也没有「已进入目标应用，开始判定」——看起来像"什么都没跑"
  （其实 tick 还在被心跳检测到，只是读界面时被掐断了）
- 手动点「依次试 7 种动作」时，**7 次动作会挤在同一秒爆发**（积压的定时任务在解冻瞬间一起执行），
  所以"第 3~7 次都读不到界面"这种现象本身就是冻结的证据
- 偶尔又"能成功"：刚切到红果、进程刚被唤醒的那几秒还没被冻，动作就生效了

对应的功能与诊断：

| 机制 | 说明 |
| --- | --- |
| **保活前台服务（常驻通知）** | 让进程变成"前台服务级"重要性，系统不会把前台服务进程放进冻结队列 |
| **加入电池优化白名单** | Honor / 小米 / OPPO 的省电策略会绕过白名单应用 |
| **应用启动管理 → 手动管理** | 荣耀机型必做，否则开机/息屏后会被"纯净后台"清掉 |
| 日志里的 `重要性=NNN` | `<=125` 前台级最稳；`400+` 缓存级=随时会被冻结，必须按上面三项设置 |
| 日志里的 `冻结=N次` | 本次会话被冻结的次数，**不为 0 就说明保活没做到位** |
| 心跳异常后自动重置计时 | 解冻瞬间不再被冷却时间挡住，立刻重新判定一次 |
| 保活服务自己的看门狗 | 出现 `⚠ 保活服务也被冻结 Xms` = 连常驻通知都没挡住，必须去改系统设置 |

排查顺序建议：先看 `[状态]` 行里的 `重要性=` 和 `冻结=`，再看有没有
`⚠ 整个进程曾被暂停`。这两样干净了，判定规则才有意义。

## 发布（维护者操作）

1. 改 `app/build.gradle` 里的 `versionCode` / `versionName`。
2. 出正式签名包（签名信息在仓库根目录 `keystore.properties`，指向 `keystore/autoswipe-release.jks`）：

        .\gradlew.bat :app:assembleRelease

   产物 `app\build\outputs\apk\release\app-release.apk`，按 `AutoSwipeHelper-<版本号>.apk`
   复制到 `dist\` 再上传。

3. 打 tag 并推送（会触发 Actions：把 main 镜像到 Gitee）：注意版本号要和第 1 步一致

        git tag v1.1
        git push origin main --tags

4. 发 GitHub Release（示例）：

        gh release create v1.1 "dist\AutoSwipeHelper-1.1.apk" --title "自动上滑助手 1.1" --notes "见 README"

   GitHub Release 建好后，Actions 里 `Mirror to Gitee` 的 `gitee-release` 任务会自动
   在 Gitee 建同名发行版、并把同一个 APK 传上去（附件名保持 `AutoSwipeHelper-<版本号>.apk`）。
   如果 tag 推送时 GitHub Release 还没建，这个任务最多等 10 分钟；等不到就只同步发行版信息，
   这时去 Actions 页面点 `Run workflow`、填上 tag 补跑一次即可。
   重复运行是幂等的：不会重复建发行版，也不会重复传附件。

**`keystore/` 和 `keystore.properties` 必须妥善备份，且永远不要提交、不要发人。**
丢了 `.jks` 或密码，就无法再给 `com.autoswipe.helper` 发布升级包（只能换包名，用户得卸载重装）。
`dist/`、`keystore/`、`*.jks`、`keystore.properties` 都已在 `.gitignore` 里。

## 真机验证结论（红果 / Honor 机型）

用「依次试 7 种动作」实测，结论：

- **「慢拖 700ms」（0.85→0.20 屏高）有效**：执行后约几秒内成功切到下一集。
- **「快滑 240ms」无效**：手势能被系统送达（日志 `手势执行完成`），但红果不认，页面不动。
- 因此策略顺序已调整为「慢拖」第一。

另外曾把 `[状态]` 与动作日志**中断 44~214 秒后一次性爆发**当成"无障碍读取被红果拖住"，
后来靠独立看门狗才确认是 **Honor 把整个进程冻结了**（见上文「根因」）。当时做的这些改动
仍然保留，它们对稳定性有帮助，但不是当时的病根：

- 判定逻辑搬到后台线程，主线程只负责下发手势（不再连累界面和手势）
- `findTargetRoot()` 优先用单次调用 `getRootInActiveWindow()`，减少跨进程次数
- 节点遍历加硬预算，单次扫描超过 800ms 会记日志
- 判定间隔超过 4 秒会记 `心跳异常`，用于区分"线程被占用"和"进程被系统冻结"

## 第八轮实测（2026-10-14 晚日志）：直播间广告能滑了，但要等 15 秒

用户反馈：这轮大部分正常、很多广告都会上滑，**只有最后一个直播间广告没有执行上滑**；
按提示回 App 点了「立即抓一次屏」，返回红果约 15 秒后那一页才被滑走。
用户的猜测是「是不是那种直播间的不会被判定为广告？」——**猜对了**。

那份现场（20:06:45，手抓整棵树）把原因说得很清楚：

| 时间 | 日志 |
| --- | --- |
| 20:06:17 | `识别到 第79集（已前进）` ← 正片播到这里，之后广告盖上来 |
| 20:06:23 | `集数=第79集(不在屏上) 可见文本=0 画面=动 广告=否 上滑提示=无 直播间=无 下一集=无 播放键=无` |
| 20:06:45 | 手抓现场：整页 64 条文本里只有一条 `领取` 被标成「可见」（它不含任何关键词，所以状态行仍是 `可见文本=0`），剧名 / 简介 / 主演 / 选集 / 分享全标着**不可见**，「第79集」的坐标在屏幕外 `[106,5277,198,2700]` |
| 20:06:58 | `页面上 15 秒没变化、屏幕上看不到集数标签（可见文本 0 条），判定为广告/直播页，补一次上滑（疑似广告页兜底）` |

也就是说：这种**全屏直播间广告页既没有「广告」二字，也没有「点击进入直播间」这类锚点，连
「上滑继续观看短剧」都不在无障碍树里**，于是 `广告=否 / 直播间=无 / 上滑提示=无`，前面所有靠文案的规则
一条也点不着；最后是**「疑似广告页兜底」在 15 秒之后**才把它滑走的（用户看到的"返回后约 15 秒才滑"就是这一段）。
顺带一提，这页 `画面=动`（直播画面一直在动），所以「画面静止检测」也救不了场。

修法：新增 **T6a「全屏直播广告快滑」**，只认一条最稳的特征 —— 正片页左上角必定有"可见的第N集"，
而这一页整页读不到任何可见文字：

| 机制 | 说明 |
| --- | --- |
| **T6a 全屏直播广告快滑（默认开，5 秒）** | 条件 = `曾经见过第N集` + `可见文本=0` + `屏幕上看不到第N集` + 树里至少还有节点 + 没有广告/直播/上滑提示/下一集/播放键锚点。满足就几秒内上滑，不再等 15 秒；动完手静默 60 秒 |
| **安静期只管正片页** | "换集安静期"（8 秒）改成只对"屏幕上看得见第N集"的页面生效 —— 全屏广告页读不到集数，不该被刚开播那几秒白白挡住 |
| **自动抓屏提前到 3 秒** | 这类"整页没有可见文字"的页面，抓屏阈值 15 秒 → 3 秒（赶在 T6a 动手之前），并且改抓**整棵树**（整页节点都标"不可见"时，只看屏幕内等于什么都没抓到） |
| **设置项** | 「全屏直播广告快滑」+「全屏广告页判定秒数」（默认 5，可调 3~60）。关掉这条也有 15 秒的「疑似广告页兜底」兜着 |

误伤风险很低：正片页永远有可见的「第N集」；红果首页 / 推荐页的卡片上带「第N集」「播放」这类文案，
也会计入可见文本，所以 `可见文本=0` 基本只在"整页盖住、读不出一个字"的广告页上成立。

## 第七轮实测（2026-10-14 傍晚日志）：倒计时广告要等 30 秒 + 全屏直播广告完全不动

用户反馈两件事：**倒计时广告倒计时结束后还要等约 30 秒才上滑**；**全屏直播广告页完全不上滑**。
这次用户按提示在直播广告页点了「立即抓一次屏」，拿到了现场。

### 一、倒计时广告：我们抢在倒计时没走完就滑，白滑还把冷却吃掉了

红果的倒计时广告文案是 `2秒后可继续上滑观看短剧` → `1秒后可继续上滑观看短剧` → `上滑继续观看短剧`。
日志里：

| 时间 | 日志 |
| --- | --- |
| 17:18:46 | 页面还写着「**2秒后**可继续上滑观看短剧」，我们就 `执行上滑`（策略 1 慢拖）→ 红果不认，白滑 |
| 17:18:48 | 「1秒后…」再次尝试 → `（同一条规则 18 秒内刚动过手、集数也没前进，这次先跳过）` |
| 17:18:51~17:19:05 | 一直想滑，一直被自己那条规则挡住 |
| **17:19:07** | 终于滑成（策略 2/7）→ **距离第一次尝试过了 21 秒** |

根因：那次"抢跑"的滑动白白占用了「同一条规则 20 秒内不重复」的冷却（那 20 秒本来是防正片被连滑的），
于是倒计时走完后还要干等。修法：

| 机制 | 说明 |
| --- | --- |
| **倒计时闸门** | 提示文案里带 `N秒后/可` 时，倒计时没走完**什么都不做**（只记一行 `广告倒计时还有 N 秒…`），也**不占用冷却**；倒计时一消失立刻滑 |
| **广告/提示类规则重试更快** | `上滑提示` / `弱提示` / `直播间广告` / `直播页无变化` 这四条的重试间隔 20 秒 → 10 秒（它们只可能在广告页上触发）；其它规则仍是 20 秒 |

### 二、全屏直播广告：卡住不动的原因找到了

用户手抓的现场（17:23:26，整棵树）很有说服力：整页 64 条文本里**只有一条 `领取` 是"可见"的**
（`[1160,939,1204,1036]`），剧名 / 简介 / 主演 / 剧评 / 收藏 / 分享全在树上但都标着**不可见**，
而且「第8集」的节点挂在**屏幕下方** `[53,5080,881,2700]`。

于是判定链全军覆没：`上滑提示=无`、`直播间=无`、`广告=否`（都看不见）；而「疑似广告页兜底」
要求 `集数 == null`，可树里那个屏幕外的「第8集」让 `集数=第8集` 一直非空 —— 兜底永远不触发，
页面就一直卡着。修法：

| 机制 | 说明 |
| --- | --- |
| **改用"屏幕上看得见的集数"** | 新增 `visibleEpisodeLabel` / `visibleCount`（只统计 `isVisibleToUser()` 且在屏幕内的节点）。兜底条件由「树里没有第N集」改成「**屏幕上**看不到第N集」+ 可见文本 ≤4 条。正片播放时「第N集」就在左上角可见，所以不会误伤 |
| **状态行更好读** | 新增 `可见文本=N`，集数只在"树里有、屏幕上没有"时标注 `集数=第8集(不在屏上)` —— 一眼就能看出当前是全屏广告页还是正片页 |

顺带说明：日志里 `17:18:57 / 17:19:05 …` 反复打印 `检测到「…」提示，执行上滑` 却看不到 `▶ 动作策略`
是正常的 —— 那些都被同规则冷却静默挡掉了（避免刷屏），不是动作失败。

## 第六轮实测（2026-10-14 中午日志）：广告过后正片被"定时滑走"

好消息：广告页这次处理得很利索，上一轮的「静默期豁免」生效了。

| 时间 | 日志 |
| --- | --- |
| 11:59:42 | `广告=是 上滑提示=有` → **当秒** `检测到「上滑继续观看短剧」提示，执行上滑` |
| 12:10:12 | 同上，`广告=是 上滑提示=有 直播间=有` → 当秒上滑（状态行显示 `安静=6s`，说明静默期确实被广告页绕过了） |

坏消息：从 12:10:12 那次广告之后，**正片开始被"定时滑走"**：

| 时间 | 事件 |
| --- | --- |
| 12:10:12 | 广告页 → 上滑（正常） |
| 12:10:25 | `直播间页面文字 10 秒无变化，补一次上滑（直播广告兜底）` ← 广告才走 13 秒，就把刚开播的正片又滑了一次 |
| 12:11:27 | 同上（62 秒后） |
| 12:12:28 | 同上（61 秒后） |

根因是 **T5「直播广告兜底」**：它的条件只有「3 分钟内见过直播间锚点」+「整页文字 10 秒没变」，
可是**正片播放时页面文字本来就不变**，于是广告一结束，这条规则就退化成"每 60 秒滑一次"的定时器
（`liveStallDisarmAt` 只静默 60 秒）。上一轮它没暴露，是因为当时 `直播间` 锚点一次都没命中过；
这次 `12:10:12` 恰好命中了 `直播间=有`，就给后面 3 分钟都上了膛。

修法：给 T5 加「**还是同一页**」的硬条件 —— 记住「看到直播间锚点那一刻、这一页的可见文字签名」，
只有当前**可见**文字和那时一模一样才允许触发。签名只统计 `isVisibleToUser()` 且坐标在屏幕内的
节点，所以屏幕外的残留节点不会来搅局。页面一变（广告结束、正片开播），T5 立刻失效。
再加一道保险：**同一页只补一次**（`liveStallDoneSig`），页面对不上就不再重复滑 —— 万一
"广告页可见文字"和"正片页可见文字"恰好一样，最多也只多滑一次，不会变成定时器。

顺手改掉的一个坑：自动抓屏原本间隔 60 秒、条件太松，8 次配额在 8 分钟内被**剧集详情页**用完
（`11:58`~`12:05` 连续 8 份全是详情页），真正的广告页反而一份没抓到。现在间隔 120 秒，
并且只打印落在屏幕里的节点（自动抓屏的 `[抓屏]` 行会标 `（仅屏幕内）`，手动按钮仍是整棵树）。

顺带记录：这份日志里 `冻结=143次` 是累计值，本轮内没有新增冻结；但
`11:58:05 扫描耗时 2120ms（节点 1，界面树偏大）` 说明在剧集详情页那种大树上读界面很慢，
会拖慢判定（详情页不是工作场景，可以忽略）。

## 第五轮实测（2026-10-14 日志）：广告页要等 8 秒 + 直播间广告不上滑

用户反馈：带「广告」二字的广告页会自动上滑，但要**停在广告页 7~8 秒**才动手；
**直播间广告（页面上没有「广告」二字）完全不上滑**；上一轮修的「广告后正片播几秒被滑」已消失。

从日志里找到的硬证据（19:13 那段，当时进程没有被冻结，数据干净）：

| 时间 | 现象 |
| --- | --- |
| 19:13:28 | `集数=第7集`，正片正常播放 |
| 19:13:30 | `识别到 第8集（已前进）` → 代码立刻点亮 8 秒"换集安静期" |
| 19:13:38 | `广告=是 上滑提示=有`，**正好在安静期结束的那一刻**才 `检测到「上滑继续观看短剧」提示，执行上滑` |

也就是说延迟不是动作慢，而是**被"换集安静期"挡住了**：红果的广告是盖在**下一页**上的，
所以 `第8集` 的文案会先出现、先把安静期点亮，真正的广告只能干等 8 秒 —— 一个 15 秒的广告
白等一半。修法：

| 机制 | 说明 |
| --- | --- |
| **广告页无视安静期** | 页面上有明确广告标记（`广告` / `跳过` / `N 秒`）时，直接跳过"换集安静期"——广告页不可能是"刚开播的正片" |
| **安静期内给提示开口子** | `上滑继续看短剧` 连续出现 3 次（约 6 秒）也放行，用于没有广告标记的广告页；残留节点一般撑不到 6 秒 |
| **广告页动作更快** | 广告页的最小动作间隔从默认 6 秒压到 2 秒；提示只需出现 1 次就动手（正片仍是 2 次） |

直播间广告这一轮**没有抓到现场**：整份日志里 `直播间=有` 出现 0 次、`[抓屏]` 一次都没有，
所以还不能确定它是"文案不在无障碍树里"还是"文案在树里但被标成不可见"。为此加了三个东西：

| 新增 | 说明 |
| --- | --- |
| **弱提示兜底（T0c，默认开）** | 提示 / 直播间锚点文案**位置确实在屏幕内**、但 `isVisibleToUser()` 返回 false 时，也按它前进；连续出现 2 次（约 4 秒）才动手，动完手静默 90 秒（防止把正片连着滑走）。第四轮为了滤掉残留节点而只认"可见"，怀疑把直播广告页的真实文案一起滤掉了，这条是补回来的口子 |
| **状态行显示 `弱`** | `广告=是/弱/否`、`上滑提示=有/弱/无`、`直播间=有/弱/无`，`弱` = 位置在屏幕内但系统标成不可见。注意 `弱` 只用于诊断和「弱提示兜底」，不会像 `有` 那样解锁其它规则 |
| **自动抓屏 + 锚点探测** | 文字停滞 12 秒以上、且页面文案很少时自动抓一份现场（60 秒最多一次、最多 8 次）；抓屏内容带**坐标和可见性**，并把所有关键文案（上滑提示 / 直播间 / 广告 / 下一集）在整棵树里搜一遍，命中的原文 + 坐标 + 可见性全部打出来 |

另外提醒一句：这份日志里 17:41 ~ 18:26 有 **208 条冻结告警**（`整个进程曾被暂停 Xms` +
`保活服务也被冻结`），那 45 分钟里一条判定、一条动作都没有 —— 那段时间后台被 Honor 冻死了，
需要重新做「应用启动管理 → 手动管理 / 自启动 / 后台活动 / 无限制省电」（见上文「根因」）。

## 第四轮实测（17:09 日志）：广告后残留节点

好消息：

- **画面静止检测（T7）真的能用**：正片播放时状态行是 `画面=动`，手动暂停后变成
  `画面=静16s`，随即触发 `画面已静止 15 秒` 并成功换集（17:11:10 / 17:11:29 / 17:11:49）。
  也就是说「一集播完卡住不动」这类场景终于有了不依赖文案的判断手段。
- 进度门槛生效：全程 `进度=读到但不动(0~2次/分)`，`播放进度停滞` 一次都没再触发。
- 冻结依然是 0 次。

剩下的真问题（17:12:52 这次）：

广告结束、正片刚开始播几秒，又被上滑了一次。日志对得上：`上滑提示=有` 在
17:12:41 → 17:12:52 一直为真，而 17:12:45（广告）已经滑过一次。原因是
**红果是上下翻页的播放流，上一页广告残留下来的「上滑继续观看短剧」「下一集」
节点会在无障碍树里挂十几秒不消失**，只看文案不看位置就会把这些残留当成
"当前页还有提示"，于是 7 秒后（冷却一到）又把刚播几秒的正片滑走。

修法（两条一起上）：

| 机制 | 说明 |
| --- | --- |
| **只认屏幕上真正看得见的节点** | 锚点节点必须先通过 `isVisibleToUser()`，且坐标要落在屏幕内；相邻页 / 残留节点一律不算 |
| **同一条规则 20 秒内不重复** | 同一条规则 20 秒内再次触发、而且中间**集数没有真的前进**，就直接跳过；一旦确认集数前进，限制立刻解除（手动测试按钮不受限制） |

备注：正片暂停超过「画面静止判定秒数」（默认 15 秒）也会被当成"视频停住了"而上滑，
这是设计使然 —— 如果你习惯暂停很久，把这个秒数调大（比如 30）即可。

## 第三轮实测（16:25 日志）：又修掉四处

这一轮的好消息：`重要性=125 冻结=0次`，**冻结问题解决了**，而且能正常识别到剧集。
暴露出来的问题都修了：

1. **正片仍被误滑**：`进度=在走` 判定太宽松。红果那种十几秒才闪一下的时间文字
   （约 5 次/分）被当成了"进度在走"，于是又每 8 秒滑一次。
   现在门槛改成 **≥15 次/分** 才算真进度，状态行同时显示 `进度=读到但不动(5次/分)`，
   一眼能看出是不是真进度。红果上这条规则实际上等于自动停用。
2. **「第N集」在几个值之间乱跳**：播放页上同时存在好几个「第N集」（上一集 / 下一集卡片），
   日志里出现 `第51集 → 第50集 → 第52集` 这种来回跳，会误判成"动作生效"。
   现在只有 **集号比见过的最大值还大** 才算前进，日志会写 `识别到 第45集（已前进）`。
   状态行还会显示 `集数=第53集(共3个)` 提示页面上有几个候选。
3. **同一种动作对着没反应的页面反复戳**：16:27:47 / 16:27:51 / 16:27:56 连续三次都是
   「慢拖」，页面一点没变。现在 **上一次动作后页面文字毫无变化 => 直接换下一种动作**
   （日志会写 `（上一次动作页面没变化，换下一种动作再试）`），7 种动作会自己轮一遍。
4. **「一集播完卡住不动」仍然无解**：红果不暴露真实进度，也没提示文案，只能靠"画面"。
   新增 **T7 画面静止检测**：用无障碍截图（`takeScreenshot`）每 2 秒抓一帧，
   缩到 16x16 跟上一帧比，变化像素少于 5% 就算"没动"；连续 N 秒（默认 15）没动
   才补一次上滑。正片播放中画面一直在动，永远不会误触发。
   状态行新增 `画面=动 / 静12s / 关`，用来确认它到底有没有在工作。

> 注意：T7 用的是无障碍截图能力（`canTakeScreenshot`，需要 Android 11+）。
> 这次改了无障碍服务配置，**必须把无障碍开关关掉再打开一次**才生效。

### 补充：广告之后正片播几秒又被滑走

反馈：广告结束后正片开始播放，几秒后又被上滑一次。日志对得上 ——
`检测到「上滑继续观看短剧」提示，执行上滑` 在 16:27:47 / 16:27:51 / 16:27:56
连续出现三次（动作写的是 `（上滑提示）`，`直播间=无`，所以那不是直播间规则）。
原因是换到下一集之后，那行提示文案还留在无障碍树里没消失，而当时只要求间隔 3 秒，
于是一换个新集就又被滑走。

修法：

| 机制 | 说明 |
| --- | --- |
| **换集后安静 8 秒** | 一旦确认「集号变大（真往前走了）」，8 秒内一律不动手（跳过广告除外）；状态行会显示 `安静=8s` |
| **提示要连续出现 2 次** | 只在当前这一帧看到提示不算数，避免刚换集时残留的提示被误判 |
| 提示规则的间隔 | 从 3 秒提高到正常冷却（默认 6 秒） |
| 事件快速通道也遵守安静期 | 系统推来的事件命中提示时，同样要等安静期结束 |

## 第二轮实测：两个真问题（2026-10-13 16:12 日志）

这一轮日志（`命中=1~3 广告=否 进度信号=有 上滑提示=无 直播间=无`）暴露了两个 bug，
都已修掉：

**问题 1：正片播放中途被误滑（已修）**

日志表现：`播放进度停滞 8 秒` 每 8~9 秒触发一次，第 44 集刚播就被滑走。

根因：状态里的「进度信号=有」只说明**页面上出现了 `12:34` 这种样子的文字**，
并不代表它在变化。而旧代码一旦读到过这种文字，就把「进度可靠」永久置为真，
于是红果这种**不把播放进度交给无障碍**的播放页，永远等不到进度推进，
8 秒后必然被判成"卡住"，然后补一次上滑——把正片一章章滑走。

修法：

- 「进度可靠」改成**看证据**：必须亲眼见过进度文字至少变化 2 次，才允许用
  「进度停滞」判断；没见过就自动停用这条规则并记一条提示。
- 状态行里 `进度信号=有/无` 改成 `进度=无 / 读到但不动 / 在走`，一眼能看出真假。

**问题 2：直播间 / 广告层完全读不到（已修）**

日志表现：`直播间=无 广告=否 上滑提示=无`，但你人在直播广告页上。

根因：旧代码只读**当前活动窗口**。而红果的广告 / 直播层常常是**覆盖在播放器之上的
一个独立窗口**（同一个包名、不同窗口）：活动窗口正好是那个几乎没有文字的播放器窗口，
于是「广告」「上滑继续短剧」这些字一个都读不到。

修法：

- 判定改成扫描目标应用**所有窗口**（活动窗口 + `getWindows()` 里所有本应用窗口），
  状态行新增 `窗口=N`，一眼能看出当时有几个窗口。
- 「抓屏」也改成把所有窗口的文字一起列出来，并新增一键按钮
  **「立即抓一次屏（6 秒后）」**：点一下 → 6 秒内切到直播广告页 → 别碰屏幕 → 回来复制日志。
- 新增第三层兜底「疑似广告页兜底」：**读不到任何剧集信息（没有「第N集」、没有锚点、
  命中节点极少）且整页文字 15 秒不变**时，才允许"盲"上滑一次，之后静默 90 秒。
  前提是本次会话见过「第N集」，说明你确实在短剧播放流里，不是停在首页。

## 直播间类广告

红果的**直播间广告**是一个独立形态：页面上常常**没有「广告」二字**，只有
「点击进入直播间」这类文案。因此单独加了锚点与规则：

- 锚点：`点击进入直播间` / `进入直播间` / `进入直播` / `直播间` / `看直播`
- 命中后执行「前进」动作（与上滑提示同一条通道），可在界面用
  「检测到直播间广告时自动前进」单独开关

但实测发现，**直播广告页底部那行「上滑继续看短剧」常常不在无障碍树里**
（日志表现为 `广告=否 上滑提示=无 下一集=无 进度信号=有`），两个锚点都可能读不到。
所以又加了第三层兜底：

- 锚点扩展到 `进直播间 / 正在直播 / 直播中 / 主播 / 人气 / 在线人数 / 送礼 / 去围观`
- **直播广告兜底**：只要最近 3 分钟内见过直播间锚点，且整页文字 10 秒毫无变化，
  就补一次上滑；触发后静默 60 秒，避免连着滑过头。开关和秒数在界面上可调。

仍然读不到时，点「立即抓一次屏（6 秒后）」抓一份直播广告页的真实文案，
把新文案补进 `LIVE_AD_TEXTS` / `SWIPE_HINT_TEXTS` 即可。

## 判定为什么改成关键词检索

早期版本每次判定会遍历整棵界面树（约 371~447 个节点），每访问一个节点都是一次
跨进程调用。红果播直播/视频时它自己的主线程很忙，这些调用会被长时间挂起，
实测出现过 `[状态]` 日志**中断 50 秒**的情况——那段时间内工具等于失明。

现在改为：

- 用 `findAccessibilityNodeInfosByText` 做关键词检索，每次判定只有约 10 次跨进程调用
- 加**事件快速通道**：直接读系统推送事件里自带的文本，零额外开销，红果读不动界面时也可能先命中
- 加**独立看门狗线程**，用来区分两种卡顿：
  - 日志出现 `⚠ 界面读取卡住 Xms` → 是我的调用被红果拖住
  - 日志出现 `⚠ 整个进程曾被暂停 Xms` → 是 ROM 把整个进程冻结了（要去关省电限制）

## 动作策略自学习

工具会**记住有效的动作**：

- 动作执行后，若集数发生变化、或「上滑继续观看短剧」提示消失 → 判定该策略有效，
  日志出现 `✔ 策略 N/7 已确认有效，之后优先使用它`
- 之后一直优先用这个策略；若它连续 3 次未见效，自动恢复轮换

## 排障：动作不生效时怎么办

实测红果遇到「直播类广告」时，底部文案是 **「上滑继续观看短剧」**（注意不是"看上滑继续看短剧"），
这时工具的触发器能命中、手势也能下发，但红果**不接受无障碍注入的手势**。

为此工具改成**轮换 7 种动作策略**，每次触发换一种，并把结果写进日志：

| # | 策略 | 说明 |
| --- | --- | --- |
| 1 | 慢拖 700ms | 0.85→0.20，模拟手指慢拖（**实测唯一有效**） |
| 2 | 快滑 240ms | 0.80→0.25 屏高，模拟快速上滑（实测无效） |
| 3 | 底部起滑 350ms | 0.92→0.30，从底部提示条附近起手 |
| 4 | 超慢长拖 1100ms | 0.88→0.12，模拟很慢很远的长拖 |
| 5 | 点「下一集」按钮 | 直接用无障碍点击按钮 |
| 6 | ACTION_SCROLL_FORWARD | 对可滚动容器下发滚动动作 |
| 7 | 双滑 | 连续两次快滑 |

用法（二选一）：

- **被动**：正常看红果，遇到广告页就**别碰屏幕**，等 30 秒左右，工具会每 3 秒自动换一种动作。
- **主动**：在 App 里点「依次试 7 种动作」，**6 秒内**切到红果的广告页并保持不动，等约 25 秒。

然后回 App 点「复制日志」。日志里重点看：

- `▶ 动作策略 N/7` 后面跟的具体策略和执行结果（`已下发` / `已接受` / `被拒绝`）
- `· 手势执行完成（系统已送达）` 还是 `· 手势被取消（…）` —— 判断是不是系统把注入手势拦了
- 动作之后有没有出现 `识别到 第N集`（集数变了说明那一种动作真的有效）

## 已知限制

- 「上滑」只对**竖屏上下滑**的短剧播放页有效；听书类走的是「点按钮」。
- 「画面静止检测」需要 Android 11+ 且无障碍服务声明了截图能力，会每 2 秒抓一帧
  （约几十毫秒 CPU），觉得费电或不需要可以在界面里关掉。
- 依赖各 App 当前版本的界面文案（「跳过」「下一集」「下一章」「继续播放」
  「第N集」「mm:ss」进度）。App 大改版后可能要更新关键词，关键词都集中在
   `app\src\main\java\com\autoswipe\helper\AutoSwipeService.java` 顶部的
  `AD_MARKERS`、`NEXT_TEXTS`、`PLAY_TEXTS`、`P_*` 常量里。
- **最重要的一条**：国产 ROM（尤其荣耀/华为）会冻结后台进程，必须把本 App 设为
  「无限制省电 + 允许自启动/后台活动 + 常驻通知开着」，否则判定和手势都不会执行。
  日志里 `冻结=` 不为 0 就说明还没设置到位。
- 这是自动化补动作，不是修改 App 本身；官方修复后本工具即可弃用。
- 未在你的手机上实测过——代码只通过了编译打包验证，规则需在真机上按日志微调。
